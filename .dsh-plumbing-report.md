# Plumbing report: adding a second (non-NVIDIA) post-trace reconstruction backend

Scope: `dev.comfyfluffy.caustica` Fabric mod, Vulkan RT path. All references are `path:line`.
Goal: a new Slang denoiser + temporal upscaler that consumes the noisy render-res trace color + guide buffers and produces the display-res scene image, slotting in where DLSS-RR (`RtDlssRr`) is today, and choosing its own render resolution. No files were modified during this investigation.

### 3.4 `renderW/renderH` vs `displayW/displayH`

- `displayW/displayH` = the native main render target (== swapchain/backbuffer size); set only in `ensureOutput` from `composite(GpuTexture, int width, int height)`'s args (`:561`, `:645`).
- `renderW/renderH` = trace + guide + continuation-queue resolution; today derived solely from `RtDlssRr.queryOptimalRenderSize` (`:930-932`) or 1:1 when RR is off. Used for image/queue allocation (`:940-946`, `:965-970`), jitter (`:1048`), trace dispatch (`:1206`, `:1211`), RR feature/evaluate (`:1216`, `:1220`), and FG's `renderW/renderH` args (`:1996`, `:2032`).
- Jitter phase count depends on the render/display ratio (`CausticaJitter.java:22-27`, `:38-41`), so a backend that changes render res automatically changes the jitter sequence.
- `CausticaJitter.prepare` is only called when a reconstruction backend is active (`:1047-1051`); a new backend must set `rrPath`-equivalent true **before** that point to keep jittering, and must consume `jitterX/jitterY` (they are also written into the world push constant ring, so the primary ray uses them — `primary.rgen.slang:225` reads `worldPush.jitter`).

### 3.5 What must change so a different backend occupies the same slot

The slot contract is exactly: **(render-res noisy rgb + 6 render-res guides + jitter + matrices) → display-res `rrOutput`, temporal history owned by the backend**.

1. **Selection**: replace the `RtDlssRr.enabled()` predicates at `:897`, `:1044`, `:1216` (and the `destroy` gate at `:1467`) with a single "active reconstruction backend" decision (e.g. an enum setting `rt.reconstruction` = `off | dlss-rr | <new>`), exposed once as a method so `ensureOutput`/`recordFrame` cannot disagree.
2. **Cache key**: `renderSizeRrEnabled`/`renderSizeRrQuality` (`:259-260`, used `:903`, `:933-934`) must become backend-agnostic: include the selected backend id and its own quality/scale inputs, otherwise changing the new backend's render scale will not rebuild at a fixed window size. Rename to e.g. `renderSizeBackend` + `renderSizeBackendKey`.
3. **Render-size policy**: replace `:930-932` with a per-backend policy; the new backend can compute its own `renderW/renderH` (e.g. round `display/scale` to a multiple of 8/16), no NGX query needed. `RtDlssRr.queryOptimalRenderSize` stays only on the RR branch.
4. **Dispatch**: in the `:1213-1235` region, branch to `RtRecon.INSTANCE.ensureFeature(...)`/`evaluate(...)` with the same `rrDone` semantics so the `blitUpscale` fallback still covers "off or runtime failure". History reset must be handled by the backend itself (RR resets via a fresh feature, `RtDlssRr.java:197`); the new backend needs its own reset trigger on resize/quality change/`resetFailureLatch`/dimension change, and `ensureOutput` already invalidates history at `:975` (`mvHasPrev = false`) on rebuild.
5. **Ownership/teardown**: add a field + lazy create next to `displayPipeline`/`bloomPipeline` (`:591-605`) and destroy it in `destroy()` around `:1498-1505` (and reset it in `resetFailureLatch`, which already exists for recovery, used at `CausticaClient.java:77`).
6. **No change needed** to guide creation, guide binding into the world pipeline (`bindGuideImages` `:855-859`; `RtPipeline.setExtraStorageImage` `RtPipeline.java:409-424`, bound range `WORLD_G_NORMAL..WORLD_G_SPEC_MOTION` `:157-160`), to `rrOutput` consumers, or to the downstream exposure/bloom/display chain — as long as the new backend writes `rrOutput` at display res and leaves `rrOutput` valid when it fails (it must, because the fallback blit only runs when the backend reports failure before writing).
7. If the new backend's pipeline is created per-resize, note `ctx.waitIdle()` at `:906` means it can be destroyed/recreated in `ensureOutput` safely.

## 4. PIPELINE TEMPLATE — boilerplate a new compute pipeline class needs

Simplest complete examples: `rt/pipeline/RtExposurePipeline.java` (313 lines, two small pass pairs with helpers) and `rt/pipeline/RtBloomPipeline.java` (357 lines, but more explanatory comments). A denoiser/upscaler with ~8 image bindings looks closest to `RtDebugPresentPipeline.create` (8 bindings) plus bloom's per-step `setImages` pattern and a sampler.

What every pipeline class does, in order (line refs are `RtBloomPipeline.java` / `RtExposurePipeline.java`):

1. **Shader resource path constant**: `private static final String SHADER = "/caustica/shaders/pipelines/bloom/main.comp.spv";` (`Bloom:49`); exposure uses `SHADER_DIR = "/caustica/shaders/pipelines/"` + name (`Exposure:37`, `:103`).
2. **Fields**: `RtContext ctx`, every raw handle (`descriptorSetLayout`, `descriptorPool`, `descriptorSets[]`, `pipelineLayout`, `pipeline`, optional `sampler`) plus `bound*View` cache fields and a `boolean destroyed` (`Bloom:59-69`, `Exposure:39-58`).

4. **Descriptor set layout**: one `VkDescriptorSetLayoutBinding.Buffer` of size `*_BINDING_COUNT` where binding index == generated constant (`Bloom:85-98`, `Exposure:83-94`); `RTDebugLabels.name(...VK_OBJECT_TYPE_DESCRIPTOR_SET_LAYOUT...)`.
5. **Descriptor pool + sets** (`Bloom:109-134`, `Exposure:97-100` via helpers).
6. **Pipeline layout with a push-constant range** of the generated size (`Bloom:136-146`; `Exposure:268-279`):
   ```java
   VkPushConstantRange.Buffer pcr = VkPushConstantRange.calloc(1, stack)
           .stageFlags(VK10.VK_SHADER_STAGE_COMPUTE_BIT).offset(0).size(BloomPushData.BYTE_SIZE);
   ```
   Note the 256-byte push-constant ceiling is a real constraint here (`RtComposite.java:169-171`); large structs go through the BDA ring instead.
7. **Shader module load**: classpath resource → `MemoryUtil.memAlloc` → `vkCreateShaderModule` (`Bloom:334-356`, `Exposure:292-312`); module destroyed right after pipeline creation (`Bloom:159`, `Exposure:107`).
8. **Compute pipeline**: `VkComputePipelineCreateInfo` with `pName("main")` (`Bloom:150-161`, `Exposure:281-290`).
9. **Sampler** if sampling (linear + `CLAMP_TO_EDGE`) (`Bloom:165-177`).
10. **Descriptor writes**: a `setImages(...)` / `setResources(...)` that no-ops when the bound views are unchanged (`Bloom:208-250`, `Exposure:138-189`), using `VkWriteDescriptorSet` with `descriptorType` matching the Slang declaration (`COMBINED_IMAGE_SAMPLER` for `Sampler2D`, `STORAGE_IMAGE` for `RWTexture2D`, `STORAGE_BUFFER` for `RWStructuredBuffer`), layout always `VK_IMAGE_LAYOUT_GENERAL` (`Bloom:267`, `:273`).
11. **`dispatch(...)`**: bind pipeline, bind set at index `*_SET`, write the generated push record into a `ByteBuffer` and `vkCmdPushConstants`, then `vkCmdDispatch` with 8x8 or 16x16 thread-group math (`Bloom:290-319`, `Exposure:191-226`). Wrap in `RtDebugLabels.scope` (`Bloom:295`, `Exposure:193`). Barriers between dependent steps use `VulkanCommandEncoder.memoryBarrier(cmd, stack)` (`Bloom:318`); the composite inserts its own barriers around the whole pass (`RtComposite.java:1213`, `:1236`).
12. **`destroy()`** idempotent via `destroyed`, destroys pipeline / sampler / pipelineLayout / pool / set layout (`Bloom:321-332`, `Exposure:228-242`).

`RtContext` helpers available: `vk()` `RtContext.java:183`, `gpuExecutor()` `:191`, `waitIdle()` `:519`, `check(int, String)` `:554`, `createStorageImage(w,h,format,label)` `:337-347`, `createBuffer(...)` `:229-234`.

MUST-implement list for a new backend pipeline class: `static create(RtContext)`, resource-set update method with view caching, `dispatch(...)`/`record(...)`, `destroy()`, and (by convention) debug names for every created object plus a `RtDebugLabels.scope` around its recording.

2. ### 5.2 Add a push-constant struct → generated Java record

`GenerateShaderRecords.groovy` reflects `shaders/layout/layout_probe.slang` (`:257-273`) and writes records to package `dev.comfyfluffy.caustica.rt.gen` (`:159-164`, output dir `:304-318`). To add a struct:

1. Declare the struct in a shared shader module — display-chain structs live in `shaders/common/display_common.slang` (see `BloomPush` there; the file header `:1-7` explains the convention) — and `[[vk::push_constant]] MyPush pc;` in the production shader (`shaders/pipelines/bloom/main.comp.slang:20`).
2. Add a dedicated probe entry point in `shaders/layout/layout_probe.slang` (one push-constant block per entry point is required by SPIR-V; comment `:36-41`), exactly like:
   ```slang
   // layout_probe.slang:89-96
   [[vk::push_constant]] BloomPush bloomPushProbe;
   [shader("compute")] [numthreads(1,1,1)]
   void probeBloomPush(uint3 id : SV_DispatchThreadID) {
       if (id.x == 0xFFFFFFFFu) { float sink = float(bloomPushProbe.mode) + bloomPushProbe.radius; }
   }
   ```
3. Register the triple in `GenerateShaderRecords.PUSH_CONSTANT_PROBES` (`:231-239`):
   ```groovy
   ["bloomPushProbe", "BloomPush", "BloomPushData"],
   ```
   (probe parameter name, Slang struct name, Java class name). Validation throws if the reflection does not match (`:244-250`).
4. Result: `dev.comfyfluffy.caustica.rt.gen.<Class>Data` with `public static final int BYTE_SIZE`, a canonical record, and `write(ByteBuffer)` generated from reflected offsets (`:150-226`). Matrix fields become `Matrix4fc` (`:60-64`), arrays get `<NAME>_CAPACITY` (`:170-172`). Only scalar readers are generated (`read`, `:199-210`, used for `ExposureStateData` `:310-311`).
5. `BYTE_SIZE` is used directly for `VkPushConstantRange.size` and `stack.malloc(...)` (`RtBloomPipeline.java:138`, `:314`), so no Java-side offset math is ever written by hand.

### 5.3 Add descriptor bindings → generated `RtBindings` constants

`RtBindings` is **not** a checked-in source: it is generated into `dev/comfyfluffy/caustica/rt/pipeline/RtBindings.java` (`GenerateRtBindings.groovy:139-150`) and every pipeline does `import static dev.comfyfluffy.caustica.rt.pipeline.RtBindings.*;` (`RtBloomPipeline.java:33`). To add a pipeline:

1. Write `shaders/pipelines/<name>/bindings.slang` following the existing convention (one declaration per binding, explicit `[[vk::binding(i, 0)]]` and `[format(...)]` for storage images):
   ```slang
   // shaders/pipelines/display/bindings.slang:1-8
   [[vk::binding(0, 0)]] [format("rgba8")]  public RWTexture2D<float4> outputImage;
   [[vk::binding(1, 0)]] [format("rgba16f")] public RWTexture2D<float4> rtImage;
   ...
   [[vk::binding(7, 0)]] public Sampler2D bloomImage;
   ```
2. Add a spec to `GenerateRtBindings.PIPELINES` (`:29-59`):
   ```groovy
   [prefix: "BLOOM", source: "pipelines/bloom/main.comp.slang",
    resources: [OUTPUT: "dstImage", SOURCE: "srcImage", EXPOSURE: "exposureImage"]],
   ```
   The map is Java-constant-suffix → Slang variable name. Generated constants: `<PREFIX>_SET`, `<PREFIX>_<SUFFIX>`, `<PREFIX>_BINDING_COUNT` (`:132-136`).
3. The generator enforces: every listed resource exists and no unlisted descriptor exists (`:88-92`); all non-WORLD resources live in exactly one descriptor set (`:97-99`); indices within a set are contiguous starting at 0 (`:100-105`). `WORLD` and `OVERLAY_*` are special-cased (`:107-131`).
4. Because `RtDebugPresentPipeline`/`RtDisplayPipeline` etc. index their binding arrays by these constants, the natural shape for a new backend shader is one set with contiguous bindings 0..N-1 (e.g. 0 = color, 1 = depth, 2 = motion, 3 = normal, 4 = albedo, 5 = specAlbedo, 6 = specMotion, 7 = output, 8 = history).

## 6. NVIDIA-ONLY GATING

### 6.1 How each NVIDIA feature gates itself today

- **`RtDlssFg` (frame generation)**: `enabled()` is config-only and defaults off (`RtDlssFg.java:29-31`; `CausticaConfig.java:673`). Availability is a separate probe: `probeAvailabilityOnce()` (`RtDlssFg.java:80-101`) → `NgxRuntime.acquire` → `lib.dlssgAvailable()`; `ensureFeature` throws, is caught, sets `failed = true` and logs "frame generation disabled" (`:146-150`). Callers: `CausticaClient.java:63-65`, `RtComposite.java:1666-1670` (`RtDlssFg.enabled()` guards the hudless capture), `:1888`, `:1996-2054`.
- **`RtReflex`**: the only feature with a proper capability gate — `enabled() = config && RtDeviceBringup.reflexEnabled()` (`RtReflex.java:69-71`), where the latch is set at device bringup from `reflexRequested() && hasDeviceExtension(VK_NV_low_latency2)` (`RtDeviceBringup.java:585`, getter `:252-253`, request gate `:430-431`). This is the model to copy.
- **`NgxRuntime`**: loads the bundled native shim, returns `null` and latches `failed` on any error (`NgxRuntime.java:55-73`, message "NGX init failed; DLSS features disabled"). There is **no vendor check**; it fails only when the shim/NGX DLL rejects the device. Shared by RR + FG; shut down once at teardown (`CausticaClient.java:112`).
- **Device extensions**: `VulkanBackendMixin.CAUSTICA_WANTED_EXTENSIONS` (`:58-67`) includes `VK_NVX_binary_import`, `VK_NVX_image_view_handle`, `VK_KHR_push_descriptor`, and each is added only if `physicalDevice.hasDeviceExtension(extension)`, else a warning ("upscaling will be unavailable", `:93-104`). No vendor check is performed — non-NVIDIA devices simply don't advertise them.
- **Vendor-name utility**: there is no `isNvidia()` helper. The only vendor check in the codebase is `"NVIDIA".equals(physicalDevice.vendorName())` in `mixin/VulkanBackendMixin.java:78` (choosing NV device-diagnostic checkpoints over AMD markers). `com.mojang.blaze3d.vulkan.VulkanPhysicalDevice` exposes `vendorName()`, `deviceName()`, `deviceType()`, `vkPhysicalDeviceProperties()`; `VkPhysicalDeviceProperties.vendorID()` is logged in `rt/VulkanDiagnostics.java:527` alongside `vendorName()`/`deviceName()`. `VulkanDiagnostics.probe(device)` (`:158`) and `RtDeviceBringup.probe(device)` (`:159`) are called once at device creation.

### 6.2 The gap a non-NVIDIA backend must fix first

`RtDlssRr.enabled()` is config-only (`RtDlssRr.java:26-28`) and defaults to **true** (`CausticaConfig.java:656`). On a non-NVIDIA device:

- `RtComposite.composite` → `ensureOutput` (`:645`) → `RtDlssRr.enabled()` true (`:897`) → `RtDlssRr.INSTANCE.queryOptimalRenderSize(width, height)` (`:930`);
- `queryOptimalRenderSize` does **not** catch (`RtDlssRr.java:135-162`): it calls `ensureInitialized` (`:209-228`) which throws `IllegalStateException("NGX runtime unavailable; DLSS-RR cannot initialize")` when `NgxRuntime.acquire` returned null;
- the exception propagates to `composite`'s `catch (Throwable t)` at `RtComposite.java:676-681`, which sets `failed = true` and logs "RT composite failed; reverting to vanilla path". `hasFailed()` (`:330-332`) then makes `VanillaRenderController.findInactiveReason` latch (`VanillaRenderController.java:121-126`).

So today there is no mechanism that makes DLSS-RR "disappear" on other vendors; the default-on RR path is a hard failure, and RT only recovers via `resetFailureLatch()` (F3+A / dimension change, `CausticaClient.java:74-78`). (`RtDlssFg` is safe only because it defaults off.)

### 6.3 Cleanest place to gate NVIDIA-only features

Two coordinated spots, mirroring what Reflex already does:

1. **Record capability once at device bringup**, where the `VulkanPhysicalDevice` is available and before any feature code runs: `VulkanBackendMixin.caustica$addDeviceExtensions(Args)` (`VulkanBackendMixin.java:88-114`) already loops over `CAUSTICA_WANTED_EXTENSIONS` with `physicalDevice.hasDeviceExtension(...)` and has `physicalDevice.vendorName()` available (used at `:78`); it also calls `RtDeviceBringup.addExtensions/...` (`:107`, `:112`). Add a `RtDeviceBringup`-style latched flag (e.g. `ngxAvailable = "NVIDIA".equals(vendorName) && hasDeviceExtension("VK_NVX_binary_import") && hasDeviceExtension("VK_NVX_image_view_handle")`) and a static getter, exactly like `reflexEnabled()` (`RtDeviceBringup.java:252-253`, set at `:585`).
2. **AND it into each feature's `enabled()`**: `RtDlssRr.enabled()` (`RtDlssRr.java:26-28`), `RtDlssFg.enabled()` (`:29-31`), and keep `RtReflex` as is. Because `RtComposite` re-reads `enabled()` every frame at `:897`/`:1044`/`:1216`, this single change makes RR fall back to `blitUpscale` (and a new non-NVIDIA backend unaffected) automatically, and fixes the hard-fail in §6.2. Also make `queryOptimalRenderSize` failure-tolerant (return 1:1 or null) rather than throwing out of `ensureOutput`, as defense in depth.
3. **Hide the UI entries** the way HDR does: `RtVideoOptions.runtimeOptions()` conditionally omits entries (`RtVideoOptions.java:54-58`, `CausticaConfig.Rt.Hdr.swapchainPqAvailable()`); a `dlssQuality()` entry should only be added when the NGX-capability latch is set. The DLSS-specific lang keys are `en_us.json:42-48`. There is no separate config-UI enumeration — `CausticaConfig.settings()` (`:37-39`) has no in-repo consumer (only the TOML writer iterates `SETTINGS` directly at `:78-80`).
